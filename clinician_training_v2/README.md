# Clinician transcript training, version 2

This is a separate training pipeline for `Qwen/Qwen3-4B-Instruct-2507`. The existing `e02_clinician_response_training.py` and helpers remain available. Version 2 learns natural spoken clinician-style replies from transcribed clinician–patient conversations. It preserves ordinary spoken phrasing and brief acknowledgments instead of polishing them into written responses.

The starting configuration targets experiments on one NVIDIA GPU with 24 GB VRAM: 4-bit NF4 QLoRA, rank-stabilized LoRA, a 4,096-token context budget, and a 256-token generation ceiling. Memory fit and response quality must be measured on your Windows computer; neither has been validated on its GPU.

## Why a separate workflow

If the untrained model's answers are already poor, training is not an adequate diagnostic. First establish whether the problem comes from the input transcript, prompt, generation setup, or the model itself. Version 2 separates preparation, baseline evaluation, training, and final testing so a successful training run cannot be mistaken for improved responses.

The pipeline:

1. Loads conversations, normalizes field names and speaker roles, and joins adjacent fragments from the same speaker.
2. Builds patient-history → clinician-turn examples without including the target or future turns in the input.
3. Keeps known participant groups and detected exact duplicates together when splitting training, validation, and test data; without participant IDs, each conversation is a separate group.
4. Flags suspect targets for review rather than automatically rewriting clinical statements.
5. Provides an optional target-review workflow, with a stricter reviewed-target requirement available in configuration.
6. Teaches only the final response and its end marker; it masks the preceding conversation from the loss.
7. Uses validation for checkpoint selection. The separate test split is reserved for the final comparison.

Read [REVIEW.md](REVIEW.md) for the implementation findings and training-method rationale.

Install a CUDA-enabled PyTorch build using the command generated by the [official PyTorch installation selector](https://pytorch.org/get-started/locally/) for Windows, pip, and the CUDA build appropriate for the installed NVIDIA driver. Install PyTorch before the remaining dependencies; a CPU-only installation will not train with the default setup.

```powershell
python -m pip install -r clinician_training_v2/requirements.txt
python -m clinician_training_v2 doctor
```

The non-PyTorch dependency versions are pinned; PyTorch is installed separately because the CUDA wheel depends on the driver and device. `doctor` prints the environment, package versions, CUDA availability, GPU, VRAM, and bfloat16 support. It does not execute a quantized forward pass, so neither that report nor installation success proves that CUDA quantization works. Native Windows is supported by current bitsandbytes. This pipeline uses PyTorch attention rather than requiring FlashAttention or an Unsloth installation.

## Input format

The current dataset is a single JSONL file inside `real_conversations`, with one conversation per nonblank line. The loader accepts either a message array or an object containing `messages` on each line. It also supports one conversation per JSON file. An object can include participant and conversation IDs, as illustrated below (write the whole object on one line in a JSONL file):

```json
{
  "participant_id": "participant_001",
  "conversation_id": "session_001",
  "messages": [
    {"speaker": "patient", "text": "I keep skipping lunch on busy days."},
    {"speaker": "clinician", "text": "What usually gets in the way of taking a lunch break?"}
  ]
}
```

Use stable pseudonymous participant IDs across visits when available. A clinician is the assistant role and a patient is the user role; these roles must not be reversed. Speaker labels should represent actual speaker turns, not arbitrary transcript chunks. The loader also accepts the legacy message-array format.

At least three groups with eligible replies are required to create train, validation, and test splits. Three is a mechanical minimum, not enough for a reliable quality estimate. `require_participant_id` defaults to `false`: when IDs are absent, each conversation record is its own group, so different lines in one JSONL file can enter different splits. Repeated explicit participant IDs keep all that person's conversations together, even across files. Without participant IDs, conversation-level splitting cannot guarantee patient separation if the same person appears in multiple conversations. Add stable IDs and set `require_participant_id` to `true` when that distinction matters.

## Prepare, with optional review

```powershell
python -m clinician_training_v2 prepare --input real_conversations --output clinician_training_v2/prepared/initial
```

The folder command automatically reads its JSONL file; no file splitting is needed. You can also pass the file directly with `--input real_conversations/your_file.jsonl`.

After updating from the earlier file-grouping implementation, regenerate the prepared data in a new directory, for example `clinician_training_v2/prepared/jsonl_v2`, and use that path for baseline, training, and evaluation. Do not reuse the old prepared splits. The updated preparation manifest uses schema version 2.

Inspect the generated `report.json`, `rejected.jsonl`, and `review_queue.jsonl`. Preparation is deterministic for the same inputs and configuration. Review coverage, split sizes, target quality, duplicate detection, and context exclusions before scheduling training.

Preparation reports text-level exclusions. Token lengths and context exclusions are measured later by `baseline`/`train` using the actual Qwen tokenizer, and written to `*_token_audit.jsonl`. Rejected targets are not in the approval queue: their rejection entries identify the original source file and zero-based message indices. Inspect these in a working copy of the source dataset, correct transcription errors there if appropriate, and prepare that copy into a new output directory.

The initial prepared dataset can be used directly; manual approval is optional. To use the optional review workflow, copy `review_queue.jsonl` to a working review file. Each review entry has an example ID, source hash, target, and decision. Edit `decision` from `pending` to `approve` or `reject`; edit `target` only when a qualified reviewer can preserve the original clinical meaning. Keep the example ID and source hash unchanged. Set `require_reviewed_targets` to `true` to require approval of every retained training and validation target before training; reject unwanted examples and re-prepare rather than leaving them pending.

Review complete turns for correctness and suitability as spoken clinician replies. Natural fillers and brief acknowledgments are retained; distinguish them from transcription errors and pathological repeated phrases. Do not invent facts, add an interpretation the transcript does not support, or rewrite speech into a different communication style. Approval concerns the actual target text, not just whether the clinician was correctly identified.

Then prepare a new reviewed dataset:

```powershell
python -m clinician_training_v2 prepare --input real_conversations --output clinician_training_v2/prepared/reviewed --reviews clinician_training_v2/prepared/reviews.jsonl
```

All output directories must be new. Existing outputs are not silently overwritten. Keep preparation inputs and settings fixed between the initial and reviewed passes so review IDs and hashes continue to identify the same source examples. The commands below use the initial dataset; substitute `prepared/reviewed` if you completed optional review.

## Check the base model first

```powershell
python -m clinician_training_v2 baseline --data clinician_training_v2/prepared/initial --output clinician_training_v2/runs/baseline
```

Read the generated responses as well as the summary. `base_probes.jsonl` contains simple arithmetic and conversational probes; `base.jsonl` contains a seeded sample of validation responses. Neither the probes nor the automatic gate score answer correctness. A response that ends naturally can still be wrong, irrelevant, or inappropriate. If baseline responses fail on simple prompts too, inspect the model/tokenizer installation and runtime before training. If simple prompts work but transcript examples fail, inspect speaker mapping, context, and target suitability.

The run folder also contains `base_summary.json`, `base_probes_summary.json`, `validation_token_audit.jsonl`, `coverage.json`, `config.json`, and `run_manifest.json`. These record end-token IDs, token counts, stop/repetition rates, target negative log likelihood, excluded examples, effective settings, data hashes, and environment versions. Teacher-forced target loss uses the full fitting validation split; generated replies use the configured `eval_examples` sample and `eval_seeds`.

## Train, then test

```powershell
python -m clinician_training_v2 train --data clinician_training_v2/prepared/initial --output clinician_training_v2/runs/run1
```

Training performs baseline validation checks before updating the adapter. By default, at least 75% of sampled responses must stop on EOS, at most 10% may contain detected repetition loops, and none may be empty. The same mechanical checks apply to the probes. If this gate fails, inspect the saved baseline files; setting `baseline_gate` to `false` is an explicit diagnostic override, not evidence that the problem is solved. Long legitimate responses can fail a short generation ceiling, so inspect `coverage.json` and target lengths before interpreting a low stop rate.

Training uses a small per-device batch, gradient accumulation, a learning-rate schedule, gradient clipping, checkpointing, and validation-based stopping/selection. The final adapter is saved under the run's `adapter` directory. It is an adapter for the specified Qwen base model, not a standalone full model. `selection.json` identifies the checkpoint selected by validation loss; `adapter.jsonl`, `adapter_summary.json`, and `comparison.json` record the resulting validation comparison.

For an interrupted run, point `--resume` to a trainer checkpoint, not the final adapter folder, and use a new output directory:

```powershell
python -m clinician_training_v2 train --data clinician_training_v2/prepared/initial --output clinician_training_v2/runs/run1-resumed --resume clinician_training_v2/runs/run1/checkpoints/checkpoint-100
```

Replace the checkpoint path with one that actually exists. Preserve the same dataset and training configuration when resuming.

Use the held-out test split once the training recipe has been selected:

```powershell
python -m clinician_training_v2 evaluate --data clinician_training_v2/prepared/initial --adapter clinician_training_v2/runs/run1/adapter --split test --output clinician_training_v2/runs/test1
```

Compare base and adapted replies on the same prompts and seeds. `blind_review.jsonl` presents randomized A/B pairs with the conversation and a review rubric; keep `blind_review_key.jsonl` closed until the assessment is complete. Judge whether they answer the patient's latest turn, use prior information accurately, avoid repetition, stop naturally, and preserve clinical meaning. Do not rank models by verbatim similarity to a single transcript reply alone. If test results influence another round of tuning, treat that set as development data and obtain a fresh final test set.

## Settings and context

The defaults live in `config.json`. Pass `--config path/to/overrides.json` to merge experiment-specific overrides with those defaults. Keep an override file per experiment. The run metadata records the effective configuration.

The default `context_policy` is `skip`: examples whose complete history does not fit are excluded and counted, rather than silently losing earlier information. This can reduce coverage of later visits or longer sessions; inspect the exclusion report. Setting `context_policy` to `recent` explicitly permits dropping oldest whole turns, preserves the system prompt and most recent turn, and reports the removals. No setting truncates a target to pretend it is complete.

Start at 4,096 context tokens. Try 8,192 only after a successful smaller run and a memory measurement. Generation length is a separate ceiling; raising context does not require asking for longer replies. If memory runs out, lower context first and keep the per-device batch at one. Increasing gradient accumulation changes the effective batch size but does not reduce the memory needed for one long example.

## Local verification and boundaries

CPU-only regression tests do not require the real transcript files or a downloaded model:

```powershell
python -m unittest discover -s clinician_training_v2/tests -v
```

Development checks included the real pinned Qwen tokenizer's prompt-prefix and EOS behavior and a tiny randomly initialized Qwen model trained on CPU through checkpoint save/reload. These checks exercise integration behavior, not the quality of the pretrained 4B model or CUDA quantization. The real conversations and trained adapter were unavailable during development. No claim is made that the new recipe improves clinical quality until the Windows GPU run and held-out human review demonstrate that improvement.

Prepared examples, review queues, generated replies, and checkpoints may contain sensitive transcript-derived information. Keep them in the ignored `prepared/` and `runs/` directories under this folder. The workflow does not require uploading conversations to an external model or publishing weights.
